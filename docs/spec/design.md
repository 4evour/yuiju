# 技术方案

## 目标

当前地点模型更接近扁平地点列表，`location.major` 承担了具体地点判断，`location.minor` 基本没有参与行为决策。后续希望把小镇地图调整为更自然的区域结构，让 `major` 表示区域，`minor` 表示区域内的具体地点。

例如咖啡店和商店不再分别作为两个独立的大地点，而是归入商业区；神社、海边等地点也应根据世界设定归入合适的区域或保留为边缘地点。

## 整体思路

地点状态继续保留 `major` 和 `minor` 两层：

- `major` 表示角色当前所在的区域，例如家、学校、商业区、公园周边、海边等。
- `minor` 表示区域内的具体地点，例如小町商店、薄暮咖啡、结灯神社等。

短期不引入无限层级地图，也不引入复杂寻路系统。当前世界主要是小镇，两层地点足够表达主要活动空间；地图关系仍然以结构化数据维护，供 prompt 和移动行为复用。

## 区域划分

当前小镇地图按以下 `major` 与 `minor` 划分：

- `HOME` / 家
  - `HOUSE` / 屋内
- `SCHOOL` / 星见丘高校
  - `CAMPUS` / 校园
- `BUSINESS_DISTRICT` / 商业区
  - `SHOP` / 小町商店
  - `CAFE` / 薄暮咖啡
- `PARK_AREA` / 公园周边
  - `PARK` / 南风公园
  - `SHRINE` / 结灯神社
- `COAST_AREA` / 海岸
  - `BEACH` / 月汐海岸

商业区和公园周边是本次重点拆分的区域。家、学校和海岸保持轻量 `minor`，主要用于让地点模型语义统一。

推荐的 `major` 区域关系：

- 家与学校相邻。
- 家与商业区相邻。
- 家与公园周边相邻。
- 学校与商业区相邻。
- 商业区与海岸相邻。

推荐的 `minor` 局部关系：

- 商业区内，小町商店与薄暮咖啡相邻。
- 公园周边内，南风公园与结灯神社相邻。
- 家、学校、海岸当前不需要内部移动关系。

## 行为选择流程

`packages/world/src/action/index.ts` 不再在外层根据 `location.major` 分发不同地点的 action。

新的流程是：

1. 汇总所有 action。
2. 每个 action 在自己的 `precondition` 内判断当前地点、状态、时间、资源等条件。
3. `getActionList` 只负责统一过滤并返回当前可执行的 action。

这样地点判断会回到具体行为内部，避免外层 action 分发表和地点层级强绑定。

## 地图与移动

地图应表达两类关系：

- 区域之间的移动关系，例如家到学校、家到商业区、商业区到海边。
- 区域内部的地点切换关系，例如商业区内从小町商店到薄暮咖啡。

移动行为只在 `minor` 之间发生，最终始终从一个完整地点移动到另一个完整地点，例如从 `HOME-HOUSE` 移动到 `BUSINESS_DISTRICT-CAFE`。

跨 `major` 移动的耗时和消耗由 `major` 区域关系决定，与目标区域内选择哪个 `minor` 无关。例如当前在 `HOME-HOUSE` 时，前往 `BUSINESS_DISTRICT-CAFE` 和前往 `BUSINESS_DISTRICT-SHOP` 使用同一条家到商业区的区域关系，耗时与消耗一致。

同一 `major` 内的移动才使用该区域下的 `minor` 局部关系，例如 `BUSINESS_DISTRICT-SHOP` 到 `BUSINESS_DISTRICT-CAFE`。

`packages/utils/src/prompt/world-map.ts` 中的地图 DSL 拆成两部分：

- `major` 区域地图 DSL：描述小镇区域之间的方位和移动关系。
- 当前 `major` 下的 `minor` 局部地图 DSL：描述当前区域内部具体地点之间的方位和移动关系。

给 Agent 的 prompt 以 DSL 作为地图关系主体，保留少量自然语言说明 DSL 的含义和层级规则。方位、耗时、体力消耗、饱腹消耗等移动约束继续通过 DSL 表达，避免用大段自然语言重复描述地图关系。

`major` 区域地图应作为小镇整体方位认知长期提供给 Agent。`minor` 地图只提供当前所在 `major` 下的局部关系，避免把所有区域内部地点一次性暴露给 Agent，降低地图信息噪声。

移动行为需要写入完整位置状态，包括 `major` 和必要的 `minor`。Agent 不直接推断任意目的地，而是在当前可用的移动 action 中做选择。

## Agent 理解方式

给 Agent 的地图信息应从单纯地点列表调整为“区域、地点功能、相邻关系”的表达：

- 区域说明：这个区域是什么。
- 地点说明：区域里有哪些具体地点，各自适合做什么。
- 可达关系：从当前位置可以去哪里，移动需要多少时间和消耗。

这样 Agent 做决策时可以同时理解“去哪里”和“为什么去那里”，减少只去高频地点、不去神社或海边这类低功能描述地点的问题。

## 本次不做的内容

本阶段只调整地点建模方向和行为选择方式，不做以下内容：

- 不引入多层嵌套地点模型。
- 不引入自动寻路算法。
- 不新增分散配置或隐式运行约定。
- 不为旧地点结构增加兼容 fallback。
- 不顺手重构与地点、地图、action 可用性无关的逻辑。
